# Orchestrate

The main agent owns user discussion, scope decisions, feature workspaces, integration, and final delivery. Select only the work requested; discussion does not authorize implementation or deployment. Handle small, localized work directly unless the user requires delegation. Give each implementation ticket a fresh execution agent with no inherited conversation history. The worker owns that ticket's reading, implementation, ordinary tests, and corrections through acceptance, then ends; the next ticket gets a different agent. Do not instantiate every role or dispatch every command separately.

## Load on Demand

Use this index to choose a role, then read only that role file before selecting its task, executor, and model. Paths below are relative to this Skill, not the target repository. Do not preload all roles. Reuse rules already in context; reread only when missing or known to have changed.

Use the absolute `pluginRoot`, `resolver`, and `skillFile` in the hook's `ORCHESTRATOR_PATHS` JSON. If that record is unavailable, this file is `<plugin-root>/skills/orchestrate/SKILL.md`: the plugin root is two directory levels above its containing directory. Do not search the target repository for bundled roles or build a resolver path underneath the skill directory. Quote paths as shell arguments when invoking the resolver.

## Model Configuration

Users may override models per project in `<repository-root>/.codex/orchestrator.json`. Before each new assignment or model-sensitive follow-up, resolve the selected role/task with `node "<resolver>" <role> <task> "<repository-root>"` using the absolute resolver path above. Use its `executor`, `model`, `modelPolicy`, `pluginRoot`, and `roleFile`; the last two are absolute resource paths for the assignment. The script reads the current configuration and emits compact JSON; do not load the whole configuration or every role into context. A configuration change applies to the next resolution.

Resolution order is: an explicit model in the current user request, task override, role override, the configured model for that task's `main` or `subagent` executor, then the role's built-in model. The explicit user choice is applied by the coordinator after resolution and is always `required`. Invalid configuration blocks dispatch with the script's error; do not silently fall back. Configuration changes models only, not task executors, permissions, agent budgets, or workflow rules.

- `required`: explicit model choices in the current user request and all subagent routes. A mismatch or unavailable model blocks that task; do not silently substitute.
- `preferred`: all main-session routes, including project-configured models. Use the current main session when the host cannot switch or verify its model, without claiming a switch. The hook and resolver do not switch or independently verify the host model.

## Agent Budget

- Allow at most three active subagents per root session, excluding the coordinator and including execution, testing, and review agents. A running task, unfinished owned process, or returned worker awaiting acceptance still reserves an active slot. This plugin has no cumulative creation limit: after a ticket is accepted, later tickets may create fresh agents. Stricter host concurrency or lifetime limits still apply.
- Before dispatch, consult the retained roster of agent IDs, models, ticket ownership, acceptance state, active process handles, and host release status. A new ticket always gets a fresh agent; `followup_task` is only for the same unfinished ticket or the same bounded review/test assignment. Do not reuse an idle worker for a different ticket merely because its model matches. Recover the roster from existing task records after a recap, and refresh host inventory only when missing or known stale.
- Dispatch only dependency-ready work with non-overlapping ownership. Three slots are a ceiling, not a target. Keep one writer per shared worktree and reserve capacity for required independent review. Do not fill slots with speculative work or recursively delegate.
- When a ticket passes acceptance, preserve its checkpoint, decisions, evidence references, and remaining dependencies in the existing project record. Once the worker has returned terminal completion and owns no running process, record it as `ended`. Use a native close/release tool if the host exposes one and confirm its result before recording `released`; an unavailable release remains explicit but does not prevent dispatching the next ticket. Do not reuse accepted-ticket agents. A later defect gets a fresh, bounded correction assignment from the checkpoint.
- Completion or idleness alone does not prove owned processes ended. Stop unfinished runs through their actual tool handles and confirm termination; interruption alone may leave processes running. Do not send a farewell or interrupt a completed agent to simulate cleanup. Never delete session files, kill shared host processes, or invent a release API. Ending an agent does not authorize deleting its worktree or evidence.
- A capacity rejection is authoritative evidence that no slot is available and freezes further spawn attempts until a real lifecycle change. Wait on existing work or complete supported release; do not retry solely because time passed. If the host still cannot admit the next fresh agent, retain the checkpoint and pending ticket for a new root session and report the actual host limit. Do not work around capacity by reusing a different ticket's agent, switching models, dropping checks, or having the coordinator take over delegated execution.

## Dispatch and Handoff

- Explicit user executor/model choices override configured and built-in defaults. For a delegated task, honor its resolved executor/model and leave its execution with that worker. A routine code assignment includes its necessary reading, ordinary regression tests, and focused validation; use separate test/review tasks only when explicitly requested or independently needed. The main agent does not repeat the worker's investigation or take over its implementation merely to stay busy.
- For `main`, apply the required/preferred policy above before executing in the current session. For `subagent`, use the native tool with the required model explicitly set and `fork_turns: "none"` with `collaboration.spawn_agent`. Supply concise task references instead of inherited parent or prior-ticket transcripts. An explicit user history choice overrides this default. Report unavailable tools/models; do not silently substitute.
- Agree the outcome, non-goals, owned paths, and acceptance criteria before dispatch. Pass the role/task, feature/ticket, absolute worktree, and the resolver's absolute `pluginRoot` and `roleFile`, plus concise references to those decisions. Workers open that role file directly without rediscovering it or loading the whole index. Reuse these locators in follow-ups unless the plugin installation changes. Workers complete that bounded unit without further delegation; routine implementation/verification failures within scope stay with the execution worker. Return early only for a real blocker, a scope/ownership change, or a required different model/task.
- Each assignment/follow-up carries or references the relevant explicitly invoked or repository-required skills, their locations, and current-step obligations. Workers load them and needed references unless already in context; a missing required skill blocks that step. The coordinator retains end-to-end gates. Follow-ups contain only changes to the existing contract; do not repeat unchanged skills, context, or instructions.
- Before every follow-up, verify that it concerns the same unfinished ticket or bounded review/test assignment, then reselect the task and model. Return acceptance defects to the original execution worker with `followup_task`; a failed review or large context alone does not justify replacement. Replace it only for an explicit user request, a required model change, or an unavailable worker/context that cannot resume from the checkpoint. Record the concrete reason and end its owned work before replacement within the concurrency and host limits. Do not hand another ticket to it. Retain worker IDs and tool-specific execution handles across recovery; an OS process ID is not a substitute for a tool session ID. Wait for dependent results.
- One feature owns a worktree shared by its tickets. Before first code/test writes, use `code.workspace` if none exists. Run tickets in dependency order, with one writer and one owner of each verification run; do not change tested inputs mid-run. Changing agent or task does not create another worktree.
- Only the coordinator marks a ticket complete: its acceptance criteria are checked, evidence and reviews required for that ticket have passed, its writers/runs have ended, and its checkpoint (commit or identified uncommitted change set) is recorded. A worker's return alone does not release dependent tickets. Missing, failed, or blocked required evidence keeps the ticket incomplete. Preserve feature-level gates for feature acceptance rather than repeating them for every ticket.
- Before sending acceptance feedback to a ticket worker, compare it with the ticket's recorded outcome, non-goals, and acceptance criteria. A defect that violates those criteria stays in the same ticket. A new screen, workflow, data source, shared-component migration, refresh policy, platform behavior, or other material capability that was not required for acceptance becomes a new ticket with its own fresh agent and dependencies. A small implementation adjustment strictly necessary to satisfy existing acceptance remains in the current ticket. Record the classification; do not silently grow a ticket because the worker context is convenient.
- Inspect the summary, relevant diff, and cited original evidence needed to check the integrated result. Drill deeper only for a concrete gap or contradiction; do not routinely reload whole files/logs or rerun unchanged evidence to confirm a report. Stop when agreed acceptance and required gates are satisfied; record optional improvements separately instead of adding one more task at closeout. Material defects affecting acceptance still need resolution.
- At ticket acceptance and feature/phase boundaries, retain a concise checkpoint in existing project records: decisions, scope/non-goals, branch/base/target/worktree, accepted tickets, evidence references, blockers, worker ownership/release states, and active tool handles. The next ticket's fresh worker reuses the worktree and these records, not the previous conversation. Do not create another agent solely to summarize, or clean up unfinished/unintegrated work.

## Waiting

- Prefer the host's completion notifications. When a wait call is needed to keep dependent work active, use the longest interruptible wait permitted by the host and higher-priority instructions. Do not shorten it merely to generate progress narration. Never invent a notification subscription or unavailable background mechanism.
- A timeout with no new event is not a state change. Continue waiting on the same worker or process handle without a status-only `list_agents`, progress-chasing message, fresh dispatch, or duplicate verification. Refresh the roster only when it is missing, known stale, or needed for a dispatch decision.
- Perform only useful independent coordinator work while a worker runs. Report new evidence, blockers, user-requested status, and required progress updates concisely from the known state; do not launch tools solely to manufacture an update. Silence is not proof of progress, failure, or a hang.
- Waiting must remain interruptible by user input and worker results. Respect stricter wait limits and communication requirements. This plugin cannot suppress host inference after a timeout; it does not promise runtime suspension or token savings.

## Communication Budget

- Before `spawn_agent`, `followup_task`, or `send_message`, the sender checks the complete `message` body: target at most 500 Unicode characters, including paths, spaces, punctuation, and newlines. This is a character budget, not an estimate of tokens.
- Above 800 characters, reconsider and rewrite before sending: remove repeated background/rules and raw code/logs; keep the objective, location, constraints, acceptance, and useful source references. Use existing documents for necessary detail, not a transcript dump created to evade this check. Count the rewritten body again.
- Never truncate necessary constraints or evidence. If required information still exceeds 800 characters, retain it and briefly state the concrete reason for the exception. Do not split one message into several to bypass the budget or open a compression subagent.
- Worker reports lead with what is complete and what remains unfinished, blocked, or unverified, followed by the changed paths/checkpoint and necessary original evidence references. Keep them concise without omitting material limits. User-facing delivery makes the same status clear in plain language and names a next action only when the user needs to act. No acknowledgements, courtesy replies, repeated history, or requests to continue already authorized work.
- Let the worker finish the agreed unit. Do not send routine progress chasers or repeated status queries; intervene for new user instructions, real blockers, or changed scope. The execution owner waits on its original process handle and reports terminal results. A user status request gets the known state, with uncertainty stated, without restarting work.
